ПРИЧИНА 3 (ИСПРАВЛЕНА): исключение в QML обрывало запуск камеры
--------------------------------------------------------------------
`qrc:/main.qml:228: Error: Cannot assign [undefined] to QSize`
Строка 228 (коммит a0b51cd, github.com/droidian/droidian-camera):
    camera.imageCapture.resolution = camera.firstFourThreeResolution
внутри `fnAspectRatio()`. Она вызывается из `Component.onCompleted`
(строка 287), а СЛЕДУЮЩЕЙ строкой (290) стоит `camera.start()`.
Необработанное исключение обрывает весь обработчик => `camera.start()`
НИКОГДА не вызывается => камера физически не запускается.
(Подтверждено gdb: `AalVideoRendererControl::startPreview()` не
вызывался ни разу.)

Первопричина: `supportedResolutions` пуст, пока камера не подключена
(m_availableSizes заполняется только в init(), т.е. ПОСЛЕ connect).

ФИКС (в нашем плагине, aalimageencodercontrol.cpp): если
m_availableSizes ещё пуст -- возвращать безопасный фолбэк
(1440x1080 = 4:3 и 1920x1080 = 16:9). QML тогда не падает, доходит до
camera.start(), камера подключается, дальше отдаются реальные размеры.
Подтверждено: ошибка main.qml:228 из лога ИСЧЕЗЛА.

После всех 4 фиксов: камера подключается, `startPreview()` реально

Рабочая гипотеза (согласуется с исходниками Camera2Client.cpp:785 --

не задан приёмник-текстура, даже в CPU-режиме кадров.
В UT это решается тем, что GL-текстуру создаёт qtvideo-node (там GL
рабочий). У нас Qt Quick GL-контекст создать не может.

ОБНОВЛЕНИЕ ПО ИТОГУ НОЧИ (проверено живьём, 2026-09-04 ~09:00):
Приватный EGL-контекст РАБОТАЕТ ("private GL context OK, texture id
= 1"), текстура отдаётся HAL, `android_camera_start_preview()`
проходит, и glReadPixels РЕАЛЬНО читает кадр без GL-ошибок:
    FIXESV32: cpu viewfinder frame 1 size QSize(3280, 2464) glErr 0
То есть весь конвейер до пикселей уже работает. ДВЕ оставшиеся
проблемы:

(а) ПАДЕНИЕ ПРИЛОЖЕНИЯ. Кадр приходит в ПОЛНОМ разрешении сенсора
    (3280x2464 = 32МБ RGBA на кадр; NV21-колбэк тоже приходил с
    data_size=12122880). Первая версия выделяла QImage заново каждый
    кадр + конвертацию в RGB32 -- падало по памяти за ~1 секунду.
    Сделано переиспользование буферов + уменьшение до 720px --
    падать стало реже, но всё равно падает. Правильное решение --
    задать HAL нормальный размер превью (android_camera_set_preview_size
    / через AalViewfinderSettingsControl), а не читать полный сенсор.

(б) ЧЁРНЫЙ ЭКРАН ДАЖЕ КОГДА КАДР ПРОЧИТАН. Причина почти наверняка
    в том, что внешнюю текстуру GL_TEXTURE_EXTERNAL_OES НЕЛЬЗЯ
    прицепить к FBO как color attachment (GLES так не умеет) --
    glReadPixels тогда читает не текстуру камеры, а пустой pbuffer,
    отсюда чёрный кадр при glErr=0. ПРАВИЛЬНЫЙ ПУТЬ: сначала
    отрисовать OES-текстуру шейдером в обычную RGBA-текстуру/FBO, и
    только потом glReadPixels -- ровно это и делает уже существующий
    в этом же файле `AalTextureBufferGraphicMapper::compileShaders()/
    renderWithShader()`, его код можно переиспользовать почти как есть.

ВСЕ ПАТЧЕННЫЕ ИСХОДНИКИ СОХРАНЕНЫ: v32/halium-extras/camera-src/
    aalvideorenderercontrol.cpp/.h  (приватный EGL + CPU-путь)
    aalcameraservice.cpp            (регистрация колбэка до connect + логи)
    aalimageencodercontrol.cpp      (фолбэк разрешений, ПРИЧИНА 3)
    egl-probe.c                     (тест-стенд, доказавший что EGL жив)
В rootfs-files застейджена СТАБИЛЬНАЯ сборка плагина (без
приватного GL-контекста): камера открывается, UI работает,
видоискатель чёрный, НО ничего не падает.

РЕАЛИЗОВАНО (детали реализации): в плагин добавлен
`AalVideoRendererControl::ensurePrivateGlContext()` -- создаёт СВОЙ
приватный минимальный EGL-контекст (pbuffer 1x1, EGL_DEFAULT_DISPLAY)
исключительно ради валидного GL texture id, который отдаётся
`android_camera_set_preview_texture()`. Отдельный C-тест-стенд
(egl-probe.c) ДОКАЗАЛ, что сырой EGL на этом устройстве полностью
рабочий (eglChooseConfig + eglCreateWindowSurface для настоящей
wl_surface, и на 400x400, и на полном 1080x2400) -- сломан именно
Qt-путь, а не драйвер.

Также в плагине уже реализован CPU-путь показа кадров
(`onPreviewFrameCB` -> `presentCpuFrame`): NV21 -> RGB32 -> QVideoFrame
-> m_surface->present(), полностью в обход GL-текстурного конвейера

3. ЧАСОВОЙ ПОЯС СЛЕТАЛ НА UTC ПОСЛЕ ПЕРЕЗАГРУЗКИ -- ИСПРАВЛЕНО
====================================================================
Причина: /etc ЦЕЛИКОМ tmpfs, а /etc/localtime и /etc/timezone не были
включены ни в один bind-mount => откат на UTC из образа каждый раз.

Фикс (событийный, БЕЗ таймера -- по требованию пользователя):
  /usr/libexec/halium-watch-timezone.sh -- подписка на D-Bus сигнал
  PropertiesChanged от systemd-timedated (gdbus monitor блокируется на
  сокете, никакого опроса), при изменении вызывает
  /usr/libexec/halium-save-timezone.sh -> /userdata/saved-timezone.txt.
  Восстановление -- первым делом в halium-restore-state.sh.
  Юнит halium-timezone-changed.service генерируется в
  halium-restore-state.sh на каждую загрузку.

ВАЖНАЯ ДЕТАЛЬ: `/etc/timezone` НЕ обновляется `timedatectl` -- читать
надо цель симлинка (`readlink -f /etc/localtime`).
ПОДТВЕРЖДЕНО ЖИВЬЁМ: пережило реальную перезагрузку (Pacific/Bougainville).

НЕ СРАБОТАЛО (записано, чтобы не повторять): systemd .path-юнит с
PathModified=/etc/localtime -- inotify следит за ЦЕЛЬЮ симлинка, смена
цели событие не порождает (не сработало даже на ручной ln -sf).

4. GPU-МОСТ android_wlegl ДЛЯ WAYLAND-КЛИЕНТОВ
====================================================================
libhybris-ный клиентский eglplatform_wayland.so требует от композитора
Wayland-глобал `android_wlegl`, которого phoc не объявляет.
Серверная реализация УЖЕ ЕСТЬ в установленной
libhybris-platformcommon.so (`server_wlegl_create(wl_display*)`).

Фикс: LD_PRELOAD-шим (android-wlegl-shim.so, ~40 строк, исходник
рядом в halium-extras/android-wlegl-shim.cpp) перехватывает
wl_display_create() в phoc и довешивает server_wlegl_create().
Подтверждено живьём: Firefox реально использует android_wlegl#109,
GPU busy ~34% при просмотре YouTube (kgsl-3d0/gpubusy).
phoc при этом не пересобирался.

Диагностическая заметка: stdout/stderr самого phoc НЕ доходит до
journalctl -u phosh.service (причина не выяснена) -- шим пишет свой лог
прямо в /tmp/android-wlegl-shim.log.

4б. FIREFOX / GPU В БРАУЗЕРЕ (частично улучшено)

РЕЗУЛЬТАТ (живьём): предупреждения `libGLESv2_adreno.so not found` и
`eglSubDriverAndroid.so not found` у Firefox ИСЧЕЗЛИ -- настоящий
драйвер Adreno теперь реально загружается. Пользователь подтвердил:
видео на YouTube стало ПЛАВНЕЕ. Остался только
`libadreno_app_profiles.so not found` -- этой библиотеки нет на
устройстве нигде вообще, она опциональная (профили тюнинга), не мешает
(то же самое зафиксировано и в UT-проекте).

ЧТО ЕЩЁ ПРОБОВАЛИ (не помогло, но зафиксировано чтобы не повторять):
  - export HYBRIS_EGLPLATFORM=wayland в обёртке Firefox
  - unset EGL_PLATFORM (Firefox наследовал EGL_PLATFORM=hwcomposer от
    phoc -- это настройка КОМПОЗИТОРА, клиенту она не нужна; убрана,
    но на результат не повлияла)
  - LD_PRELOAD-шим, подменяющий eglChooseConfig и подставляющий рабочий
    конфиг, если приложение получило ноль (идея пользователя, исходник
    сохранён: halium-extras/camera-src/egl-config-fallback-shim.c).
    НЕ СРАБОТАЛ: шим В ПРОЦЕСС ЗАГРУЖАЕТСЯ (4 записи в /proc/PID/maps),
    но его eglChooseConfig не вызывается ни разу -- GLVND
    (/usr/lib/aarch64-linux-gnu/libEGL.so.1.1.0) диспатчит вызовы к
    вендорному ICD ВНУТРИ СЕБЯ, через собственную таблицу указателей,
    минуя обычное разрешение символов -- LD_PRELOAD такие вызовы не
    перехватывает в принципе. Вывод на будущее: подменять EGL-функции
    через LD_PRELOAD в GLVND-системе бесполезно.
  - __EGL_VENDOR_LIBRARY_FILENAMES=.../10_libhybris.json -- принудительно
    оставить только hybris-ICD (в процессе реально загружены ОБА:
    libEGL_libhybris.so.0.0.0 И libEGL_mesa.so.0.0.0, была гипотеза, что
    GLVND выбирает Mesa). Тоже не помогло -- та же ошибка.

ПОЛЕЗНЫЙ ФАКТ ИЗ ЭТИХ ПОПЫТОК: в /proc/PID/maps живого Firefox теперь
реально присутствует `/vendor/lib64/egl/libEGL_adreno.so` -- то есть
НАСТОЯЩИЙ драйвер Adreno загружен в процесс (после фикса путей). Раньше
его там не было вообще. Отказ происходит уже ПОСЛЕ загрузки драйвера,
на этапе выбора конфига.
Firefox по-прежнему пишет `Failed to create EGLConfig for WebRender!`
и откатывается на software WebRender (`Fallback WR to SW-WR`).

ЭТО РОВНО ТА ЖЕ СТЕНА, ЧТО И У QT (см. ниже): изолированный C-тест
(egl-probe.c, лежит в halium-extras/camera-src/) на этом же устройстве
УСПЕШНО получает конфиг ЛЮБОГО вида -- включая RGBA8888 +
depth24 + stencil8, то есть ровно то, что просят Firefox и Qt -- и
успешно создаёт eglCreateWindowSurface для настоящей wl_surface (и на
400x400, и на полном 1080x2400). А внутри реальных приложений тот же
запрос не проходит. Значит дело НЕ в драйвере, НЕ в наборе конфигов и
НЕ в переменных окружения, а в чём-то специфичном для этих процессов
(вероятнее всего -- многопоточность: EGL/wl_display из нескольких
потоков, тогда как тест однопоточный). Это следующая точка
расследования и для Firefox, и для камеры ОДНОВРЕМЕННО -- причина у
них общая.

6.3 РЕАЛЬНЫЙ ФИКС КОДА: OES-текстура не читалась через glReadPixels
    (ПРИЧИНА (б) из раздела "остаётся нерешённым" выше) -- ИСПРАВЛЕНО
--------------------------------------------------------------------
`AalTextureBufferPixelReadMapper::map()` раньше цепляла OES-текстуру
камеры напрямую к FBO как color attachment и читала её glReadPixels --
GL_TEXTURE_EXTERNAL_OES так в принципе нельзя использовать (спека
GL_OES_EGL_image_external не гарантирует этого), на практике читался
пустой pbuffer. Фикс: `compileShaders()`/`renderWithShader()` подняты
в базовый класс AalTextureBufferMapper (были только в
AalTextureBufferGraphicMapper), PixelReadMapper теперь СНАЧАЛА рисует
OES-текстуру шейдером в обычную GL_TEXTURE_2D (`ensureResolveTexture()`),
и уже её читает glReadPixels -- ровно то, что уже работало в
Graphic-мапере для EGLImage-пути. Одновременно убрана переаллокация
`m_pixelBuffer` на КАЖДЫЙ кадр (была ПРИЧИНА (а), падение по памяти) --
буфер теперь переиспользуется, пока размер не меняется. Плюс в
`AalViewfinderSettingsControl::chooseOptimalSize()` заменено слепое
"взять sizes[1]" на выбор размера, ближайшего по площади к 1280x720
(на этом HAL sizes[1] мог оказаться близко к полному сенсору).
Код собирается чисто, задеплоен и живьём проверен -- ПРИЛОЖЕНИЕ БОЛЬШЕ
НЕ ПАДАЕТ, работает стабильно долго. Но видоискатель всё ещё чёрный
(см. 6.4).

6.4 РЕАЛЬНЫЙ ФИКС КОДА: AalGLTextureBuffer всегда репортила
    GLTextureHandle -- диагностировано ещё в прошлую сессию, но НИКОГДА
    не было применено в коде. ПРИМЕНЕНО, но видоискатель ВСЁ ЕЩЁ чёрный
--------------------------------------------------------------------
В памяти прошлой сессии (раздел "Камера: видоискатель чёрный --
продолжение расследования") уже было верно диагностировано: конструктор
`AalGLTextureBuffer` хардкодил `QAbstractVideoBuffer::GLTextureHandle`
НЕЗАВИСИМО от реального маппера -- из-за этого QtMultimedia всегда
выбирала GL-текстурный QSGVideoNode (не может работать под
QT_QUICK_BACKEND=software), а не CPU/QImage-совместимый узел, который
реально вызвал бы наш (уже рабочий, см. 6.3) map(). Этот диагноз был
верным, но ФИКС РАНЬШЕ НЕ БЫЛ ПРИМЕНЁН В КОДЕ (только описан в тексте).
Применено сейчас: добавлен виртуальный `handleType()` в
AalTextureBufferMapper (по умолчанию GLTextureHandle, для обратной
совместимости с Graphic-маппером), PixelReadMapper переопределяет его в
NoHandle, AalGLTextureBuffer теперь спрашивает `mapper->handleType()`
вместо хардкода.

РЕЗУЛЬТАТ ПОСЛЕ ФИКСА: видоискатель ВСЁ РАВНО чёрный. Добавлена точечная
диагностика прямо в map() (счётчик вызовов + статус FBO + glReadPixels
error + первый пиксель кадра) -- ЗА ВЕСЬ ЗАПУСК ПРИЛОЖЕНИЯ map()
ВЫЗВАН 0 РАЗ. То есть теперь стена ещё глубже, чем казалось: дело не в
том, что map() читает пустоту -- Qt Quick вообще НИ РАЗУ не пытается
прочитать буфер нашего кадра, хотя `updateViewfinderFrame()` точно
вызывается (видно по CLAUDE_DEBUG вокруг startPreview/updateCaptureReady)
и `m_surface->present(frame)` в ней должен отрабатывать без ошибок (нет
ни одного "Failed to start viewfinder"/"Invalid frame" в логе).

Проверена и ОТБРОШЕНА гипотеза, что виноват старый GL-only плагин
`libshadervideonode.so` (`qt5/plugins/video/videonode/`, не из apt,
перенесён из параллельного UT-проекта) -- временно переименован в
`.disabled`, приложение перезапущено, видоискатель остался чёрным,
map() всё так же 0 вызовов -- значит дело не в конкурирующей
регистрации video-node-фабрики. Плагин возвращён на место (переименован
обратно), т.к. отключение ничего не дало.

Загадочная деталь (не разгадана, вероятно нерелевантна): в логе

7.1 ПОЛНЫЙ ПЕРЕПИСАН AalVideoRendererControl НА CALLBACK-РЕЖИМ HAL
--------------------------------------------------------------------
Ключевое переосмысление: ночной успех 2026-09-04 (раздел 0) шёл через
CALLBACK-режим Camera1 API (`PREVIEW_CALLBACK_ENABLED`, сырые NV21-кадры
через `on_preview_frame_cb`), а НЕ через GL-текстуру
(`android_camera_set_preview_texture`), которую весь код в разделах 1-6
пытался безуспешно дорендерить. Кода для callback-режима нигде не
нашлось (ни в v32/halium-extras/camera-src/, ни в live `.so` на
устройстве, ни в build-chroot) -- он существовал только в памяти той
сессии и был безвозвратно потерян. Переписан с нуля:
  - Убраны AalTextureBufferGraphicMapper и AalTextureBufferPixelReadMapper
    (весь GL/EGLImage/glReadPixels-конвейер, который так и не смог
    отрендериться под QT_QUICK_BACKEND=software) -- код удалён, не просто
    закомментирован, вместе с shared compileShaders()/renderWithShader()
    в базовом классе.
  - Новый AalCallbackFrameMapper: держит обычный CPU-буфер RGB32,
    заполняется НАПРЯМУЮ из NV21-колбэка (без единого вызова GL/EGL),
    `handleType()` = NoHandle (см. п.6.4).
  - `ensurePrivateGlContext()` ОСТАВЛЕН -- текстура по-прежнему нужна
    ТОЛЬКО чтобы удовлетворить `haveValidPreviewWindow()` в HAL, реальные
    пиксели через неё больше не идут.
  - `startPreview()`: `android_camera_set_preview_texture()` (для HAL-
    проверки) + `android_camera_set_preview_callback_mode(cc,
    PREVIEW_CALLBACK_ENABLED)` (реальная доставка) + `start_preview()`.
  - `stopPreview()`: добавлен симметричный `PREVIEW_CALLBACK_DISABLED`.
  - `init()`: регистрирует `listener->on_preview_frame_cb =
    &onPreviewFrameCB` (новый статический колбэк).
  - NV21->RGB32: Y-плоскость + перемежённая VU (NV21), BT.601 fixed-point
    (298*C ± ... >> 8), без библиотек, ручной цикл.

7.2 НАЙДЕНА И ИСПРАВЛЕНА РЕАЛЬНАЯ ПРИЧИНА "stack corruption detected
    (-fstack-protector)" НА ПЕРВОМ ЖЕ РЕАЛЬНОМ КАДРЕ: qWarning() В
    ПОТОКЕ HAL-КОЛБЭКА
--------------------------------------------------------------------
Первая рабочая версия падала МГНОВЕННО и 100% воспроизводимо на первом
же вызове `onPreviewFrameCB()` с сообщением "stack corruption detected
(-fstack-protector)". Перебраны и ОТБРОШЕНЫ гипотезы: (а) переполнение
буфера в NV21->RGB32 цикле -- вручную пересчитаны все границы для
реального кадра 1440x1080, индексы сходятся день в день, овнрфлоу нет;
(б) data race на m_width/m_height между потоками (setSize() из GUI-потока
без лока vs чтение в колбэке) -- добавлена синхронизация тем же
QMutex, крэш НЕ исчез; (в) лок, удерживаемый между map()/unmap()
(если Qt вызовет unmap() без парного map() -- unlock() незалоченного
QMutex, UB) -- переделано на копирование в scratch-буфер без
пересекающего вызовы лока, крэш ВСЁ РАВНО НЕ исчез.

**Decisive-тест**: колбэк оставлен ПОЛНОСТЬЮ пустым (только один
`qWarning()` и `return`, без единого обращения к data/m_mapper) --
"stack corruption" ВСЁ РАВНО случался. Значит дело не в бизнес-логике
вообще. Убран ЕДИНСТВЕННЫЙ оставшийся qWarning() из тела колбэка --
крэш ИСЧЕЗ полностью (проверено: приложение стабильно живёт 15+ секунд
без единого падения, раньше падало за 1-2 секунды).

**Вывод/правило на будущее**: HAL зовёт `on_preview_frame_cb` из потока
с маленьким и/или нестандартным стеком (типично для binder-колбэк-
потоков в Android/hybris) -- сложное форматирование QDebug/QString
внутри `qWarning() << a << b << c` само по себе достаточно "дорого" по
стеку, чтобы переполнить такой поток и разбить canary. **ПРАВИЛО:
НИКАКИХ qWarning()/qDebug() внутри onPreviewFrameCB() и всего, что оно
вызывает синхронно (updateFromNV21()) -- только чистая арифметика.**
Диагностический счётчик кадров (`g_previewFrameCount`, простой
`std::atomic<int>`, инкремент без логирования) читается и печатается
ТОЛЬКО из updateViewfinderFrame() (GUI-поток, безопасно).

7.6 ПОБОЧНАЯ НАХОДКА: разблокировка экрана по паролю вообще не

Обнаружено случайно при проверке лока экрана. Два независимых бага:

1. `/etc/shadow` был `group=root` вместо `group=shadow` -- setgid-хелпер

   `chgrp shadow /etc/shadow` -- добавлено в начало
   `halium-restore-state.sh` (сразу после remount,rw), т.к. /etc --

10. Утечка памяти в minimediaservice -- растёт неограниченно при
    активной работе камеры, доводит систему до OOM за ~10-15 минут
====================================================================
Живьём обнаружено: `/system/bin/minimediaservice` (android-сервис
внутри LXC-контейнера, часть медиа/аудио-моста для камеры) разрастался
до 2.6GB RSS (47% всей RAM) примерно за 10-15 минут работы камеры
(свежий процесс -- около 17MB). Как только свободная память падает
почти до нуля, системный OOM-killer начинает убивать всё подряд
(клавиатуру phosh-osk-stevia, session.slice, иногда сам phoc) -- отсюда
"приложение остановлено" и пропадающий интерфейс камеры/экрана.

ВРЕМЕННЫЙ ЛЕЧЕНИЕ (не фикс, а обход): убить процесс minimediaservice
(`kill -9`), он тут же респаунится с нуля (17MB). Делать это стоит
превентивно, если камера использовалась дольше нескольких минут
подряд, а не только когда система уже начала тормозить.

НЕ ИССЛЕДОВАНО: где именно в native-цепочке NV21-callback preview
происходит утечка (сам AAL-плагин, весь этот вечер тестировавшийся,
или сторона minimediaservice, куда плагин не заходит вообще). Нужно
исследование в следующей сессии, если камера снова будет активно
тестироваться подолгу -- иначе риск повторной OOM-спирали.

13. в35 -> в36: ДЕЙСТВИТЕЛЬНАЯ причина "пароль спрашивает, но не
    принимает" -- НЕ то, что думали раньше (2026-09-05)
====================================================================
На в35 (эксперимент на базе в31) require-unlock=true наконец-то
заработал (после отключения halium-disable-lockscreen.service), но
пароль перестал приниматься -- "user unknown" от unix_chkpwd, как и
раньше на в33. В этот раз разобрались до конца через живой strace,
прицепленный к phosh (`strace -f -tt -e trace=execve,openat,access -p
<phosh_pid>`) прямо во время попытки разблокировки:

    execve("/sbin/unix_chkpwd", ["/sbin/unix_chkpwd", "phablet", "nonull"], ...)
    ...
    openat(AT_FDCWD, "/etc/shadow", O_RDONLY|O_CLOEXEC) = -1 EACCES

setgid-бит на unix_chkpwd сам по себе в порядке (-rwxr-sr-x root shadow,
никакого nosuid на /usr или /). Причина ПРОСТАЯ: `/etc/shadow` в
реальности была группы `root`, а не `shadow`, несмотря на то, что
halium-fix-shadow-group.service (см. раздел 12.4) должен был это
починить. Сервис оказался **disabled** -- ln -sf для его enable-
симлинка стоял в update-binary РАНЬШЕ строки
`cp -a "$EXTRAS"/rootfs-files/. "$ROOTFS_MNT/"`, и был защищён `[ -f
... ] &&`-гейтом -- на момент проверки файл юнита ещё физически не
существовал в $ROOTFS_MNT (bulk-copy кладёт его позже), гейт всегда
проваливался, ln -sf никогда не выполнялся. Тот же самый "ordering
bug", что уже был задокументирован для halium-disable-lockscreen.
service/halium-restore-state.service в этом же файле -- их обход
(unconditional ln -sf, без "-f" гейта, симлинк просто "висит в
воздухе" до появления цели) применён и здесь.

ВЫВОД: пункт 12.4 из прошлого раздела ("причина НЕ найдена") был
неверным диагнозом -- дело было не в PAM/NSS/setgid, а в том, что
фикс группы shadow банально НИКОГДА не запускался на застейдженных
файлах из-за этого ordering bug в update-binary. Живой chgrp shadow
/etc/shadow сразу решал проблему на живом устройстве каждый раз именно
потому, что группа была не выставлена вообще, а не потому что фикс не
срабатывал сам по себе.

Проверено и ИСКЛЮЧЕНО в процессе диагностики: NoNewPrivileges=no на
phosh.service и user@1000.service (не причина); отсутствие SELinux
AVC-denial в dmesg (не SELinux); mount-опции / и /usr без nosuid (не
mount-баг); NSS/getpwnam через python3 -- работает нормально (не NSS).

ВАЖНЫЙ УРОК: при добавлении НОВОГО enable-блока (`ln -sf ... в
multi-user.target.wants`) в update-binary -- проверять его позицию
ОТНОСИТЕЛЬНО `cp -a "$EXTRAS"/rootfs-files/.` перед тем, как решать,
нужен ли "-f" гейт вообще. Если блок раньше bulk-copy -- гейт нельзя
использовать, надо unconditional ln -sf.

15.4. КЛЮЧЕВАЯ НАХОДКА -- у контейнера ДВА РАЗНЫХ представления
    /system/lib64/libcameraservice.so:
    - Хостовый путь `/var/lib/lxc/android/rootfs/system/lib64/...`
      (то, что видно СНАРУЖИ контейнера, через /dev/mapper/system)
    - Путь `/proc/<pid_внутри_контейнера>/root/system/lib64/...`
      (то, что РЕАЛЬНО видит процесс ВНУТРИ контейнера)
    Прямая перезапись файла по ПЕРВОМУ пути (даже пережившая
    перезагрузку, хеш совпадал) НЕ отражалась во ВТОРОМ -- подтверждено
    живьём: `md5sum /proc/<minimediaservice_pid>/root/system/lib64/
    libcameraservice.so` показывал СТАРЫЙ хеш, пока файл не был
    перезаписан именно через `/proc/<pid>/root/...` (эквивалент записи
    изнутри контейнера). После этого запись подтверждённо видна и
    новому respawn'у minimediaservice. ВЫВОД: для этого устройства
    /system внутри контейнера -- это НЕ то же самое, что
    /var/lib/lxc/android/rootfs/system снаружи (два разных mount'а/вида
    одного и того же раздела) -- любой будущий фикс файлов внутри
    /system ОБЯЗАН писать через `/proc/<живой_pid_в_контейнере>/root/...`
    (или `lxc-attach -n android -- ...` с последующей записью изнутри),
    а НЕ через хостовый /var/lib/lxc/android/rootfs путь.

16.1. КОРНЕВАЯ ПРИЧИНА (100% подтверждено дизассемблированием). На
    устройстве реально установлен НЕ ванильный libhybris, а форк
    droidian/libhybris ветка `feature/next/lindroid-drm`, пакет
    `libhybris 0.0.5.53-1+droidian1+git20260715172057.60b7e82.
    next.lindroid.drm` (проверено `dpkg -l`/`dpkg -S`). В файле
    `hybris/egl/egl.c` этой ветки функция `eglGetConfigAttrib()`
    написана вручную (в отличие от `eglGetConfigs()`/`eglChooseConfig()`,
    которые реализованы через макрос `HYBRIS_EGL_IMPLEMENT_FUNCTION*` и
    САМИ вызывают `hybris_egl_get_real_display(dpy)` перед обращением к
    реальному vendor-драйверу) и передаёт `dpy` В VENDOR-ДРАЙВЕР БЕЗ
    ЭТОГО РАЗВОРАЧИВАНИЯ:

        ret = (*_eglGetConfigAttrib)(dpy, config, attribute, value);

    Для платформы EGL_PLATFORM_WAYLAND_KHR значение `dpy` -- это
    указатель на внутреннюю обёртку libhybris:

        struct _EGLDisplay { EGLDisplay dpy; EGLNativeDisplayType display_id; };

    а не настоящий хэндл дисплея вендора (Adreno). Функция
    `hybris_egl_get_real_display()` как раз и делает разворачивание
    (`return ((struct _EGLDisplay *)display)->dpy;` для wayland-ws),
    но `eglGetConfigAttrib()` её не вызывает. Vendor-драйвер получает
    мусорный хэндл и возвращает НУЛЕВЫЕ атрибуты для ВСЕХ конфигов
    (RGBA=0000, surfaceType=0, renderable=0) -- отсюда чёрный
    видоискатель: `eglChooseConfig()` формально "находит" конфиг (эта
    функция дисплей разворачивает правильно), но реальный рендеринг
    через такой "пустой" конфиг не работает.

16.2. Между приложением и libhybris стоит ещё один слой -- GLVND
    (`/usr/lib/aarch64-linux-gnu/libEGL.so.1`, диспетчер, который
    грузит `libEGL_libhybris.so.0` И `libEGL_mesa.so.0` одновременно,
    см. `LD_DEBUG=libs`). GLVND-вендор-библиотека `libEGL_libhybris.so.0`
    (сборка `--enable-glvnd`) НЕ экспортирует обычные имена функций
    (`eglGetConfigAttrib` и т.п.) вообще -- только ОДНУ точку входа
    `__egl_Main()` (см. `hybris/egl/glvnd/eglglvnd.cpp`), через которую
    GLVND один раз регистрирует таблицу указателей функций и потом
    дёргает их напрямую по указателю, а не по символьному имени. Из-за
    этого ЛЮБАЯ попытка починить баг через LD_PRELOAD (переопределение
    `eglGetConfigAttrib`/`eglGetProcAddress`/`eglGetPlatformDisplay` на
    лету) НЕ РАБОТАЕТ ПРИНЦИПИАЛЬНО -- перехватывать нечего, вызов идёт
    через уже зарезолвленный указатель внутри `.so`. Проверено живьём:
    несколько вариантов LD_PRELOAD-шима либо ничего не давали (при
    "мимо" перехвате), либо роняли камеру сегфолтом (при попытке
    подменить чужой дисплей на "развёрнутый" в функции, которая внутри
    самого GLVND дёргается по указателю, а не по символу).
