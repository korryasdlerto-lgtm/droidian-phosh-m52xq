# v31: seat-сессия, фонарик, сохранение яркости, USB-скрипт жарил телефон (2026-09-02)

## Контекст

Живая прошивка v30 (полный вайп Data+Metadata, первый по-настоящему
чистый флеш этой версии update-binary). Пользователь сообщил три
проблемы сразу после первой загрузки: Wi-Fi не подключается ("не
предлагает пароль"), кнопка питания не блокирует экран, фонарик не
горит.

## Баг 1: недостающая seat-сессия у Phosh (Wi-Fi + кнопка питания)

### Диагностика

`journalctl -b` на живой системе показал каскад:
```
phosh[...]: Setting backlight on HWCOMPOSER-1 failed: GDBus.Error:org.freedesktop.login1.NotYourDevice: Your session has no seat, refusing.
gnome-session-service[...]: Could not get session path for session. Check that logind is properly installed and pam_systemd is getting used at login.
gnome-control-center[...]: Failed to add and activate connection '1': Not authorized to control networking.
```

`loginctl list-sessions` показал сессию `c1` (seat0, tty7, leader PID
уже мёртв) в состоянии **`State: closing`** — застрявшая/осиротевшая
logind-сессия. `phoc` (компоситор) захватил seat напрямую через
seatd, но у пользовательской gnome-session/Phosh-сессии полноценной
активной logind-сессии не было, поэтому PolicyKit отказывал
NetworkManager в авторизации (`Not authorized to control networking`)
на КАЖДЫЙ тап по сети в списке Wi-Fi.

### Настоящая причина

В `update-binary` (строки ~845-854) блок, создающий symlink
`seatd.service` в теневой копии `/data/system-data/etc/systemd/system/
multi-user.target.wants/`, проверял только `[ -d "$SYSDATA_UNITDIR" ]`
(верхняя папка `.../system`), но НЕ создавал вложенную
`multi-user.target.wants` перед `ln -sf`. У соседнего блока
(`halium-start-container-delayed.service`, строки ~818-826) есть свой
`mkdir -p "$SYSDATA_UNITDIR/multi-user.target.wants"`, но он выполняется
только внутри `[ -f .../halium-start-container-delayed.service ]` —
а этот файл давно удалён из образа (заменён на
`halium-container-autostart.service` ещё в v28), так что условие
ложное и `mkdir -p` для `multi-user.target.wants` никогда не
выполнялся.

Баг был латентным ВСЕ предыдущие флеши, потому что
`/data/system-data/etc/systemd/system/multi-user.target.wants`
переживала как "наследие" от старых версий скрипта (когда
`halium-start-container-delayed.service` ещё реально существовал и
создавал эту папку) — вылезло только сейчас, при первом за сессию
полностью чистом форматировании `/data`.

При флеше в логе `update-binary` видна прямая ошибка:
```
ln: cannot create symbolic link from '../seatd.service' to '/data/system-data/etc/systemd/system/multi-user.target.wants/seatd.service': No such file or directory
```

### Фикс (постоянный, в update-binary v31)

```sh
if [ -d "$SYSDATA_UNITDIR" ]; then
    mkdir -p "$SYSDATA_UNITDIR/multi-user.target.wants"
    rm -f "$SYSDATA_UNITDIR/multi-user.target.wants/seatd.service"
    ln -sf "../seatd.service" "$SYSDATA_UNITDIR/multi-user.target.wants/seatd.service"
fi
```

### Живой обходной фикс (применён на устройстве без переflеша)

1. Создан недостающий symlink вручную.
2. `systemctl restart phosh.service` (НЕ `systemctl restart
   systemd-logind` — это запрещено, ломает активную libseat-сессию
   phoc).

После рестарта `loginctl session-status` показал новую сессию с
`State: active`, `Seat: seat0`. **Подтверждено живьём**: Wi-Fi
запросил пароль и подключился, кнопка питания стала блокировать
экран.

## Баг 2: фонарик не горит (не связано с seat-багом)

### Диагностика

`flashlightd` (`/usr/libexec/flashlightd`, D-Bus `org.droidian.
Flashlightd`) управляет вспышкой через libhybris/gstreamer-droid →
Android CameraHAL. На этом устройстве `vendor.camera-provider-2-6` не
поднимается (нет EFS-калибровок мультикамеры — та же причина, что и
у неработающей камеры). `strings /usr/libexec/flashlightd` не
содержит вообще никаких sysfs-путей — весь путь идёт через
camera-provider, обхода на уровне самого демона нет.

### Реальный рабочий узел (найден в параллельном UT-проекте, там же
### подтверждён живьём 2026-07-16, `halium-fix-torch-perm.sh`)

`/sys/devices/virtual/camera/flash/rear_flash` — Samsung-специфичный
магический-значение узел (НЕ `led:torch_0`, тот подтверждённый
тупик — запись принимается, света нет, dmesg молчит). За ним стоит
отдельная PMIC/charger-микросхема `sm5714-fled`. Протокол: `0`=выкл,
`100`=torch on. Полностью в обход CamX/camera-provider.

**Подтверждено живьём на этом устройстве 2026-09-02**: `echo 100 >
rear_flash` → полная цепочка в dmesg (`sm5714_store: value=100 ->
fled_torch_enable(1) -> sm5714_fled_control: Torch mode & used
gpio(1)`) и реальный физический свет (подтверждено пользователем).

Права на узел уже чинятся существующим (давно перенесённым, но не
проверенным до сегодня) `halium-fix-torch-perm.service` — владелец
уже `phablet` на живой системе, дополнительных прав не требовалось.

### Фикс: shim вместо настоящего flashlightd

`org.gnome.Flashlightd`/`org.droidian.Flashlightd` D-Bus интерфейс
простой (интроспекция подтверждена живьём): метод
`SetBrightness(u bvalue)`, readwrite свойство `Brightness`. Написан
`halium-rear-flash-shim.py` (GLib/Gio, `usr/libexec/`) — держит то же
имя шины, на `SetBrightness`/`Properties.Set` пишет в `rear_flash` и
рассылает `PropertiesChanged` (важно: рассылать сигнал НУЖНО из ОБОИХ
путей — и метода, и `Properties.Set`, иначе кнопка в шторке Phosh
визуально отстаёт от реального состояния — поймано живьём при первом
тесте).

`usr/lib/systemd/user/org.droidian.Flashlightd.service` (rootfs-files,
переопределяет пакетный юнит) указывает `ExecStart` на
`python3 /usr/libexec/halium-rear-flash-shim.py` вместо настоящего
`/usr/libexec/flashlightd`.

**Подтверждено живьём**: кнопка в шторке зажигает и гасит фонарик
корректно, синхронно отражая состояние.

## Баг 3: сохранение яркости ловит транзитное значение при затемнении

### Диагностика

`halium-save-state.sh` вызывается `halium-save-state.timer`
безусловно каждые 2 минуты и писал сырое текущее значение
`/sys/class/backlight/panel0-backlight/brightness` в
`/userdata/saved-brightness.txt` без всякой проверки контекста. Если
тик таймера попадал на момент анимации затемнения экрана перед
блокировкой/сном (gsd-power плавно снижает яркость до минимума перед
выключением), в файл сохранялась именно эта транзитная почти-нулевая
яркость, а не реальная пользовательская.

### Фикс

Перед записью проверяется `IdleHint` активной seat0-сессии через
`loginctl show-session ... -p IdleHint --value` — logind выставляет
`IdleHint=yes` именно во время dim-to-sleep перехода. Сохранение
пропускается, если сессия idle:

```sh
_seat0_session=$(loginctl list-sessions --no-legend 2>/dev/null | awk '$4=="seat0"{print $1; exit}')
_idle="no"
if [ -n "$_seat0_session" ]; then
    _idle=$(loginctl show-session "$_seat0_session" -p IdleHint --value 2>/dev/null)
fi
if [ "$_idle" != "yes" ]; then
    cat /sys/class/backlight/panel0-backlight/brightness 2>/dev/null > /userdata/saved-brightness.txt
fi
```

**Подтверждено живьём**: сохранённое значение совпадает с реальным
текущим при активной (не idle) сессии.

## Баг 4: `halium-force-usb-developer-mode.service` жарил телефон и жрал батарею (найдено 2026-09-02, отдельная сессия)

### Контекст

Пользователь сообщил: телефон всегда горячий, заряжается 4 часа вместо
2, "как будто что-то ест батарею даже во время зарядки".

### Диагностика

`top` показал `PID 4954 "sh"` — **23.5% CPU непрерывно**, 3:47 накопленного
CPU-времени за 23 минуты аптайма. Дочерний процесс
`halium-force-usb-developer-mode.service` (`systemctl status` — CPU:
**38 минут за 25 минут аптайма**, больше 100% ядра постоянно).

Причина в самом скрипте (`/usr/libexec/halium-force-usb-developer-mode.sh`,
основной supervisor-цикл службы, `Type=simple`+`Restart=always`, крутится
весь аптайм): 21 июля в этот ЖЕ постоянный скрипт были добавлены ТРИ
ВРЕМЕННЫХ отладочных захвата для одноразового живого расследования
~3-секундного дрейфа `rndis.usb0 -> mass_storage.usb0`:
- `udevadm monitor --udev --property` (бесконечный поток, пишет в
  `/userdata/usb-udev-monitor.log`)
- `dmesg -w` (бесконечный поток, `/userdata/usb-dmesg-monitor.log`)
- `dbus-monitor --system` (**весь** системный D-Bus трафик, бесконечно,
  `/userdata/usb-dbus-monitor.log`)

Их забыли убрать после завершения того расследования. Живое
подтверждение: `/userdata/usb-dbus-monitor.log` вырос до
**2 083 417 917 байт (~2ГБ) всего за 26 минут** одной загрузки
(~1.3МБ/сек постоянной записи на диск). Плюс основной поллинг-цикл сам
по себе дёргает `dbus-send`/`systemctl show` **каждую секунду**,
бесконечно (до 3600 итераций = час, потом рестарт службы и по новой),
потому что скрипт документирует: RNDIS-грант живёт ровно ~3с и
откатывается сам, независимо от вмешательства.

### Фикс

Три блока (`udevadm monitor`/`dmesg -w`/`dbus-monitor --system`,
включая их комментарии-обоснования от 21 июля) полностью удалены из
скрипта — они были чисто диагностическим инструментом для уже
закрытого расследования, не нужны в продакшене. Основной
поллинг-цикл (проверка `c.1`/`ip`/`ssh`/`pm` раз в секунду и
восстановление RNDIS/SSH при дрейфе) оставлен как есть — он
функционально нужен для стабильного SSH-доступа на этом устройстве.

**Подтверждено живьём**: после деплоя (`mount -o remount,rw /`, замена
файла, `remount,ro /`, `systemctl restart`) — новый процесс за 16
секунд работы показал **148мс** CPU-времени (было бы ~38мин за
эквивалентный промежуток по старой ставке). Load average упал с 3.5 до
1.7 за минуту. Три фоновых процесса убиты (`kill -9` по PID, НЕ
`pkill -f` — тот словил что-то лишнее и оборвал саму SSH-сессию),
гигантские логи удалены (`/userdata/usb-dbus-monitor.log` 2ГБ,
`usb-dmesg-monitor.log` 90МБ, `usb-udev-monitor.log` 7.7МБ).

## Побочная находка: suspend всё ещё никогда не срабатывает

`/sys/kernel/debug/suspend_stats` показывает `success: 0, fail: 0` за
весь аптайм — устройство ни разу даже не ПЫТАЛОСЬ уйти в реальный сон.
Это САМО ПО СЕБЕ уже объясняет разряд/нагрев независимо от
USB-скрипта (SoC работает "в полную" круглосуточно, без глубоких
энергосберегающих состояний) — старое расследование
(`FIXES-V22-SUSPEND-INVESTIGATION.md`, 2026-07-26) нашло, что реальный
`systemctl suspend` падает с `EBUSY` через ~360мс, и заподозрило
крашащиеся Android HAL-сервисы (composer, suspend@1.0, bluetooth, gnss,
fingerprint, mediametrics) как причину — та же картина воспроизведена
живьём сегодня (101-125 zombie-процессов этих же сервисов, цикл
падения каждые ~30с в первые минуты после загрузки, замедляется, но не
прекращается). Пойман (chmod 755 на crash_dump32/64 на время теста,
затем обратно 000) реальный краш `zygote64` (SIGABRT) через фоновый
монитор logcat — детальный анализ backtrace ещё предстоит.

Параллельно найдено (не портировано, только для справки): в UT netd
падает НЕ нативным крашем, а осознанным `exit(1)` из-за отсутствующих
eBPF-объектов (APEX `com.android.tethering` намеренно спрятан в этом
проекте, см. `feedback_no_tethering_resolv_apex`) — патчили netd,
живьём подтвердили, что даже с рабочим патчем главная проблема
(разряд/выключение) НЕ решается, netd НЕ является главной причиной,
патч полностью откатили. Не тратить время на netd ради suspend/жары.

**Статус**: не исправлено, USB-скрипт был первой конкретной находкой
и уже устранён. Реальная причина `suspend` EBUSY (какой конкретно HAL
держит PM-ресурс занятым) — открытый вопрос, следующий шаг.

## Камера: реальный дефект в qt5-cameraplugin-aal, не env-фикс (2026-09-02)

`.desktop`-wrapper для `droidian-camera` (env `HYBRIS_LD_LIBRARY_PATH`/
`ANDROID_ROOT`) добавлен, но НЕ решает проблему полностью — приложение
перестаёт busy-loop'иться, но видоискатель всё равно не показывает
картинку. Причина найдена через `QT_LOGGING_RULES="qt.qpa.*=true"`:
`AalTextureBufferGraphicMapper` (код из ОТДЕЛЬНОГО пакета
`qt5-cameraplugin-aal`, не самого `droidian-camera`) вызывает
`eglChooseConfig()` для offscreen/pbuffer-конфига при конвертации
кадра камеры в GPU-текстуру -- `Cannot find EGLConfig`. Проверено во
ВСЕХ комбинациях `EGL_PLATFORM=hwcomposer`/`QT_QPA_PLATFORM=wayland`/
`wayland-egl` -- результат идентичный независимо от переменных.
Вывод: EGL-реализация hwcomposer на этом железе (та же, через которую
работает phoc-компоситор) поддерживает только WINDOW-поверхности, не
PBUFFER/offscreen -- нужен код камеры (eglCreateImageKHR +
EGL_NATIVE_BUFFER_ANDROID вместо offscreen pbuffer), а не переменные
окружения.

**Важно**: в параллельном UT-проекте видоискатель `lomiri-camera-app`
(тот же `cameraplugin-aal`, апстрим `qtubuntu-camera`) ТОЖЕ не
работает (`ФИКСЫ_ДЛЯ_В50.txt`, 27.08: "ОСТАЮЩАЯСЯ ПРОБЛЕМА (НЕ
РЕШЕНО): видоискатель всё равно чёрный", `m_surface is NULL`) --
разные симптомы (у нас EGLConfig, у них NULL surface), но оба
нерешены независимо. Нет рабочего образца скопировать.

`camera-provider` при этом реально МОЖЕТ подниматься: init-бинарник
на этом конкретном `boot.img` содержит зашитую строку "Service
'vendor.camera-provider-2-6' WAS TOTALLY DESTROYED BY SASHA!" --
компилированная (не rc-скрипт) блокировка ctl.start для этого
сервиса, происхождение не установлено (не в UT-доках, не в текущем
`system/core/init` дереве -- видимо, более старая точечная правка).
Запуск бинарника НАПРЯМУЮ (в обход init) показал: `camera-provider`
стабилен (не крашится), реально регистрируется в HAL (`lshal` ->
`ICameraProvider/legacy/0`), находит камеры (`Added camera 0-4`) --
проблема НЕ в отсутствующих EFS-калибровках, как считалось раньше, а
именно в EGL pbuffer-несовместимости выше по стеку. `cameraserver`
отдельно отключён штатно (`cameraserver_HYBRIS_DISABLED` -- обычное
для Halium-портов переименование, не проблема).

## Телефония: DIAG-драйвер отсутствует в ядре (2026-09-02)

`ofono-sailfish` с `binder`-плагином уже установлен и настроен
ПРАВИЛЬНО (то самое решение из параллельного UT-проекта,
`/usr/lib/aarch64-linux-gnu/ofono-sailfish/plugins/binderplugin.so`,
`ofonod ... -P ...,binder` реально запущен) -- но `GetModems`
возвращает пустой список. Через `strace` на прямом запуске
`/vendor/bin/hw/rild` (падает с exit(1) каждые ~5с, `init.svc.
ril-daemon=restarting`, НИ ОДНОГО вывода в logcat -- падает раньше
инициализации логирования):
```
write(1, "diag:failed to connect to diag socket\n Diag_LSM_Init: Failed to open handle to diag driver, error = 111")
exit_group(1)
```
`/dev/diag` не существует НИ на хосте, НИ в контейнере. Без rild ни
один `IRadio` HAL-сервис не регистрируется (`service list` в
контейнере пуст по radio) -- то есть даже "современный" binder-путь
ofono всё равно зависит от того, чтобы vendor-`rild` поднялся и
зарегистрировал сервис.

**Поиск драйвера**: `drivers/char/diag/` (полноценный Qualcomm DIAG
char-driver) отсутствует НЕ ТОЛЬКО в нашем дереве ядра, но и во ВСЕХ
проверенных community-форках для этого SoC (LineageOS/android_kernel_
samsung_sm7325, PixelExperience-Devices/kernel_samsung_sm7325) --
кастомные AOSP-сборки массово вырезают этот драйвер. Нет и готового
прекомпилированного `diag.ko`/`diagchar.ko` нигде в проекте (включая
уже собранную папку `/userdata/kernel-modules-fixed/`, ~85 модулей).
**Скачан и проверен официальный GPL-релиз ядра Samsung**
(opensource.samsung.com, SM-M526BR, Android 13,
`M526BRXXS5CXE2`/`M526BXXS5CXE3`, `Kernel.tar.gz` ~196МБ + `Platform.
tar.gz` ~42МБ, лежит в `/home/sasha/Загрузки/SM-M526BR.zip`) -- **даже
там `drivers/char/diag` нет**. Значит DIAG на этом поколении чипов
(SM7325, QSSI/Android13) -- закрытый Qualcomm-компонент, который
Samsung не обязана публиковать даже по GPL, либо архитектура вообще
сменилась (см. ниже).

**УТОЧНЕНО ЧЕРЕЗ STRACE (2026-09-02, важный пересмотр)**: реальная
цепочка вызовов `libdiag.so` внутри `rild`:
```
openat("/dev/diag", O_RDWR|O_CLOEXEC) = -1 ENOENT
socket(AF_UNIX, SOCK_SEQPACKET, 0) = 8
connect(8, {sa_family=AF_UNIX, sun_path=@"..."}, 110) = -1 ECONNREFUSED
```
Библиотека СНАЧАЛА пробует классический char-device `/dev/diag`
(ENOENT), затем падает на fallback через **абстрактный Unix-сокет**
(`ECONNREFUSED`, а не "устройство отсутствует") -- то есть нужен не
обязательно драйвер ядра, а, возможно, просто userspace-демон/сервис,
слушающий на этом сокете. Точное имя сокета из strace прочитать не
удалось (выглядит как все нулевые байты -- либо обрезано, либо имя
длиннее буфера strace).

**ПОДТВЕРЖДЕНО**: аппаратный DIAG-канал физически СУЩЕСТВУЕТ --
`/sys/firmware/devicetree/base/__symbols__/modem_diag` и
`funnel_mq6_dup_in_modem_diag` есть в живом devicetree (glink/SMD-канал
между apps- и modem-процессором). Просто нет моста ядро/userspace,
который бы подключал этот канал к `/dev/diag` ИЛИ к тому сокету.
Никакого отдельного diag-роутинг-демона (`diag_mdlog` и т.п.) на

## ПРОРЫВ (тот же вечер, 2026-09-02): рабочий userspace-мост через rpmsg/glink

Не потребовался ни kernel-драйвер, ни поиск точного имени
abstract-сокета -- нашёлся путь короче.

**Ключевая находка**: `/dev/rpmsg_ctrl0..3` уже существуют на этом
ядре (по одному на каждый сопроцессор: `rpmsg_ctrl0`=adsp,
`rpmsg_ctrl1`=wpss, `rpmsg_ctrl2`=cdsp, **`rpmsg_ctrl3`=modem** --
подтверждено через `/sys/dev/char/253:N` -> `readlink -f`). Framework
`rpmsg_chrdev` в ядре реально работает (видны живые каналы DATA1-4/DS/
IPCRTR и т.д. для модема в `/sys/bus/rpmsg/devices/`) -- просто канал
"DIAG" не создаётся АВТОМАТИЧЕСКИ при загрузке, его нужно явно
запросить через `ioctl(RPMSG_CREATE_EPT_IOCTL)` с именем канала.

(Ложный след по пути: DT-символ `modem_diag` -- это НЕ тот канал, это
ARM CoreSight debug-trace источник (`qcom,coresight-dummy`,
`coresight-name: coresight-modem-diag`), полностью не связан с
DIAG-протоколом для RIL.)

**ПОДТВЕРЖДЕНО ЖИВЬЁМ**: написана маленькая statically-linked
aarch64 C-программа (`halium-extras/telephony-diag-bridge/
rpmsg_diag_bridge.c`, собрана `aarch64-linux-gnu-gcc -static`),
открывает `/dev/rpmsg_ctrl3`, делает
`ioctl(fd, RPMSG_CREATE_EPT_IOCTL, {name="DIAG", src=0xFFFFFFFF,
dst=0xFFFFFFFF})` -- **модемная прошивка реально откликнулась с
первой попытки** (имя канала "DIAG" -- правильное, стандартное для
Qualcomm-платформ), материализовался `/dev/rpmsg0`.

**ВАЖНЫЙ НЮАНС** (пойман живьём): endpoint существует ТОЛЬКО пока
открыт файловый дескриптор, которым он создан -- если создающий
процесс завершается (закрывает fd), `/dev/rpmsgN` исчезает.
Программа переписана держать fd открытым бесконечно (`pause()` в
цикле) вместо create-and-exit -- работает как постоянный
демон-держатель канала.

Дальше: `lxc-attach -n android -- ln -sf /dev/rpmsg0 /dev/diag`
(симлинк нужно создавать ВНУТРИ контейнера -- у него своя видимость
`/dev`, хотя сами device-ноды с хоста видны напрямую без bind-mount).
Запуск `/vendor/bin/hw/rild` после этого:
- **БЕЗ моста**: падает мгновенно, `exit(1)` за миллисекунды,
  `Diag_LSM_Init: error = 111` (то же самое, что было весь вечер).
- **С мостом**: `rild` реально ЖИВЁТ несколько секунд (`ps` показывает
  `state=S`, потом `state=D`, `WCHAN=qcom_glink_create_ept` --
  застревает внутри ядра в СВОЁМ собственном вызове создания
  endpoint'а), затем через ~5-10с сам тихо завершается (без записи в
  dmesg с явной причиной).

**Гипотеза незакрытого вопроса**: вероятен конфликт -- канал "DIAG"
на стороне модема, похоже, не рассчитан на ДВУХ одновременных клиентов
(наш мост уже держит endpoint через `rpmsg_ctrl3`, и `rild`
одновременно с этим ПОВТОРНО пытается создать/согласовать свой
собственный endpoint через открытие `/dev/diag`/glink-протокол
изнутри). Возможные направления для следующей сессии:
1. Проверить, не нужно ли МОСТУ закрыть/освободить endpoint сразу
   после появления `/dev/rpmsgN`, оставив только САМ device-файл (без
   держащегося ctrl-fd) -- вдруг rpmsg_char реализация этого ядра
   всё-таки не требует держать создающий fd (наблюдение про "исчезает
   без держателя" может быть специфично для КОНКРЕТНОГО способа
   тестирования, не универсальным).
2. Проверить, не нужен ли rild ЭКСКЛЮЗИВНЫЙ доступ к устройству без
   стороннего "владельца" ctrl-канала -- возможно, стоит вместо
   постоянного stand-alone моста написать маленький systemd-сервис,
   который создаёт endpoint ПРЯМО ПЕРЕД стартом rild (через
   `ExecStartPre`) и передаёт владение, либо через bind-mount, либо
   через сам факт наличия готового `/dev/rpmsgN` без держащего его
   постороннего процесса.
3. `strace -f` НА САМ `rild` в момент зависания в `D`-состоянии не
   снят -- неизвестно, на КАКОМ именно syscall/ioctl он блокируется
   бесконечно (простой `strace` может не пробиться через D-state).
4. Даже если `rild` доживёт до полной инициализации -- ещё не
   проверено, зарегистрируется ли реальный `IRadio` HAL-сервис и
   увидит ли его `ofono`'s binder-плагин (`GetModems`) -- следующий
   шаг ПОСЛЕ того, как сам `rild` перестанет виснуть/падать.

Файл с рабочим кодом сохранён:
`halium-extras/telephony-diag-bridge/rpmsg_diag_bridge.c` (в этой
папке v31, НЕ подключён пока ни к update-binary, ни к systemd-юниту --
это ещё живой прототип, не готовое к продакшену решение).

**ДОПОЛНИТЕЛЬНО пойман важный нюанс сразу после написания выше**:
проверили `/dev/rpmsg0` ПОСЛЕ неудачной попытки `rild` -- **устройство
исчезло, хотя процесс-мост (`rpmsg_diag_bridge`) всё ещё жив и держит
свой ctrl-fd открытым** (`ps` подтвердил, PID жив, состояние `S`).
Это меняет гипотезу конфликта: похоже, попытка `rild` создать
СОБСТВЕННЫЙ endpoint с тем же именем "DIAG" не просто "конфликтует
одновременно", а **разрушает/замещает** уже существующий endpoint
моста на уровне ядра/glink -- даже при живом держателе исходного fd.
Возможно, канал в принципе рассчитан только на ОДНОГО клиента, и
kernel-драйвер `rpmsg_char`/`glink` разрешает второй `create_ept`
вызов, разрывая первый.

**Следующая сессия, начинать СРАЗУ отсюда** (обновлено 2026-09-02,
поздний вечер, после ~8 живых циклов тест/SSR):

**Пойден и найден точный код ошибки в ядре**:
`drivers/rpmsg/rpmsg_char.c::rpmsg_eptdev_open()` вызывает
`rpmsg_create_ept()` заново при КАЖДОМ `open()` устройства (не только
при создании через ctrl-ioctl) -- если `rpmsg_create_ept()` вернёт
NULL, `open()` отдаёт `-EINVAL`. Именно это и происходит:
`openat("/dev/diag", O_RDWR|O_CLOEXEC) = -1 EINVAL`.

**Экспериментально подтверждено (переключение с 111 на 22 -- реальный
прогресс)**: с "голым" мостом (создающий процесс держит ctrl-fd
открытым ИЛИ закрывает сразу после создания -- обе версии протестированы,
`/dev/rpmsg0` переживает закрытие ctrl-fd, это подтверждено) --
`rild` больше НЕ падает на "ECONNREFUSED к сокету" (той изначальной
проблемы, с которой начали вечер), а доходит до реального открытия
`/dev/diag`. Иногда (примерно 1 раз из ~6-8 попыток) `open()` реально
УДАЁТСЯ, и `rild` работает несколько секунд БЕЗ ЕДИНОЙ ошибки в логе
(живьём подтверждено -- 8-секундный `timeout` истёк молча, никакого
"Diag_LSM_Init: Failed"). Но чаще -- `EINVAL` на каждой попытке
(2 попытки подряд с интервалом ~5с, потом `rild` сдаётся и падает).

**Гипотеза (не подтверждена до конца)**: похоже на race condition в
самой glink-негоциации между AP и модемом -- возможно, канал "DIAG"
на удалённой (модемной) стороне не готов принять НОВЫЙ `create_ept()`
сразу после того, как предыдущая попытка (даже неудачная) уже
взаимодействовала с ним, и нужна пауза/явный сброс состояния перед
повторной попыткой. Пауза в 3с перед запуском `rild` НЕ помогла
устранить нестабильность (проверено).

**ВАЖНОЕ ПРЕДУПРЕЖДЕНИЕ О РИСКЕ (для следующей сессии)**: за вечер
поймано МИНИМУМ 3 подтверждённых SSR (subsystem restart) модемного
сопроцессора (каждый раз `/dev/rpmsg_ctrlN` номер сдвигается на
следующий -- ctrl3->ctrl4->ctrl3(новый minor)) -- SSR сам по себе
безопасен (штатный механизм самовосстановления Qualcomm, устройство
не перезагружается целиком), НО ОДИН РАЗ (первый тяжёлый совместный
запуск `rild`+полновесный `strace -f` под большой нагрузкой) вызвал
**полную перезагрузку всего устройства** (`sys.boot.reason=reboot`,
pstore пуст -- не kernel panic, похоже на софтверный триггер от
каскада нестабильности). Дальнейшие живые попытки на этом канале --
реальный, повторяющийся риск SSR при каждой попытке, и подтверждённый
(хоть и реже) риск полной перезагрузки при более тяжёлой нагрузке
(полный `-f` strace + rild одновременно). Продолжать только на трезвую
голову, с пониманием этого риска, желательно НЕ поздним вечером.

**Следующие шаги** (по приоритету):
1. Выяснить точную причину intermittent EINVAL -- нужен доступ к
   glink-уровню (`/sys/kernel/debug/rpmsg`/`ftrace` события
   `rpmsg_*` если включены в этом ядре) чтобы увидеть, что именно
   отвечает удалённая сторона в момент неудачного `create_ept()`.
2. Прямой `strace -f` НА САМ `rild` (не только на мост) в момент,
   когда он висит в `D`-состоянии (`qcom_glink_create_ept`) --
   технически уже пробовали общий strace, но НЕ specifически
   ловили именно момент D-state зависания отдельно от EINVAL-цикла.
3. Проверить гипотезу про exclusivity: возможно, нужно, чтобы
   ИМЕННО `rild` (а не наш helper) был первым и единственным, кто
   когда-либо трогал канал за весь boot -- т.е. интегрировать
   создание endpoint'а как `ExecStartPre` НЕПОСРЕДСТВЕННО перед
   стартом `ril-daemon` внутри контейнера (через host->container
   мост, аналогично camera.ko/GPU-bridge паттерну), а не как
   отдельный ручной эксперимент после множества предыдущих попыток
   на этом же канале за this boot.
4. Даже если `rild` стабилизируется -- ещё не проверено, реально ли
   через него идёт содержательный DIAG-трафик, или он просто "тихо"
   держит устройство открытым без реальной передачи данных (открытие
   без ошибки не равно полноценной работе).

Рабочий код (обе версии -- держащая fd и закрывающая сразу):
`halium-extras/telephony-diag-bridge/rpmsg_diag_bridge.c` (в этой
папке v31). Дополнительный sniffer-инструмент (не задействован
полноценно из-за конфликта повторного open()):
`halium-extras/telephony-diag-bridge/rpmsg_diag_sniff.c`.

## ФИНАЛЬНАЯ (на сегодня) находка: упёрлись в закрытую прошивку модема

После ещё ~4 живых попыток (единый непрерывный запуск create+symlink+
strace без пауз между шагами, чтобы исключить гонку по времени между
отдельными SSH-командами) -- `EINVAL` воспроизводится СТАБИЛЬНО почти
всегда (5-6 раз подряд из ~7 суммарных попыток за вечер), единственный
успешный запуск (0 ошибок за 8с) теперь выглядит как везучая
случайность, а не закономерность.

**Прочитан код `qcom_glink_create_ept()`
(`drivers/rpmsg/qcom_glink_native.c:1429`)**: сначала ищет, не
анонсировал ли УЖЕ сам модем канал "DIAG" в списке `rcids` (remote
channel ids). Если нет -- вызывает `qcom_glink_create_local()`
(наша сторона САМА инициирует открытие, шлёт `RPM_CMD_OPEN` через
`qcom_glink_send_open_req()`) и, судя по коду, синхронно ждёт ответа
модема. Раз "DIAG" не появляется среди авто-зарегистрированных каналов
при обычной загрузке (в отличие от DATA1-4/DS/IPCRTR, которые
регистрируются сами) -- модемная прошивка, похоже, НЕ ожидает
получить `RPM_CMD_OPEN` для "DIAG" в таком виде/такой
последовательности, и не подтверждает его вовремя (или вовсе).

**Вывод**: дальше упираемся не в нашу сторону (kernel/rootfs), а в
ЗАКРЫТУЮ прошивку модема (MPSS) и её ожидания по последовательности/
протоколу открытия diag-канала -- то, что раньше делал закрытый
userspace-стек через `drivers/char/diag/diagchar_core.c` (у него,
вероятно, была своя, более сложная процедура инициализации канала,
не сводящаяся к одному `RPMSG_CREATE_EPT_IOCTL`). Без реверс-инжиниринга
точной последовательности handshake'а (что шлёт диагстек ДО открытия
канала -- возможно что-то через QMI/другой канал сначала
"регистрирует"/"включает" diag на стороне модема) дальнейшее слепое
подбирание `ioctl`-вызовов малоперспективно.

**Статус на конец сессии**: реальный, воспроизводимый (хоть и редко)
success ПОДТВЕРЖДАЕТ, что путь принципиально верный -- канал
физически существует и МОЖЕТ открыться. Но для стабильной работы
нужно либо (а) точно воспроизвести протокол handshake'а модема
(требует реверс-инжиниринга или документации MPSS-прошивки, которой
нет), либо (б) найти alternative способ его инициализации (например,
через QMI-команду до попытки открытия rpmsg-канала -- возможно, diag
на этой прошивке включается/регистрируется через отдельный QMI-сервис
перед тем как glink-канал становится доступным для открытия).

  строк `android_wlegl_server_buffer_handle#NNN still attached`
  (до #282!) -- реальные кадры камеры теперь физически передаются от
  HAL в приложение через Wayland-EGL мост. Раньше (без
  camera-provider) такого не было вообще -- сразу голая ошибка EGL
  без единого кадра. `Cannot find EGLConfig` (известный pbuffer-баг в
  `qt5-cameraplugin-aal`, см. секцию выше) всё ещё блокирует финальный
  рендер видоискателя, но САМ ПАЙПЛАЙН КАМЕРЫ теперь реально живой и
  передаёт данные -- значительно ближе к рабочему состоянию, чем
  предполагалось вечером.

**Побочный эффект, стоит проверить в следующий раз**: раз
camera-provider теперь стабильно работает штатно, стоит перепроверить
и настоящий `flashlightd` (не наш `rear_flash`-шим) -- возможно, он
теперь тоже заработает сам по себе, раз его реальная зависимость
(camera-provider/gstreamer-droid) больше не блокирована.

### Глубокое расследование EGLConfig-бага (та же ночь, продолжение)

Найден ТОЧНЫЙ код, печатающий "Cannot find EGLConfig, returning null
config" -- это НЕ закрытый Adreno-драйвер и не наш код, а сам
**Qt** (`qtbase/src/gui/opengl/platform/egl/qeglconvenience.cpp`,
функция подбора конфига под `QSurfaceFormat`):
```cpp
do {
    eglChooseConfig(display(), configureAttributes..., &matching);
    ...
} while (q_reduceConfigAttributes(&configureAttributes));
if (!cfg)
    qWarning("Cannot find EGLConfig, returning null config");
```
Qt уже сам перебирает много вариантов требований (уменьшая размеры
цветовых каналов и т.д.) в цикле -- закрытый драйвер отказывает на
ВСЕХ попытках. Проверена гипотеза `EGL_PLATFORM=wayland` (правильный
backend для клиента, в отличие от ошибочно применённого раньше
`hwcomposer` -- нашли, что `DEFAULT_EGL_PLATFORM` в `libhybris` без
явной настройки = `"null"`, а не `"wayland"`) -- НЕ помогло, тот же
результат.

**КЛЮЧЕВАЯ ЗАЦЕПКА для следующей сессии**: в логе `droidian-camera`
видны СОТНИ строк `android_wlegl_server_buffer_handle#NNN still
attached` -- это ОТДЕЛЬНЫЙ, УЖЕ РАБОТАЮЩИЙ протокол-расширение
Wayland (`android_wlegl`, реализован в wlroots/phoc), специально
созданный для передачи Android GPU-буферов (ANativeWindow/gralloc)
компоситору В ОБХОД обычного клиентского EGL-пути. То есть кадры
камеры (`AalTextureBufferGraphicMapper`'s `EGLImageKHR`+
`EGL_NATIVE_BUFFER_ANDROID`) реально доходят до компоситора успешно.

Провал `eglChooseConfig` -- ОТДЕЛЬНАЯ, более ранняя стадия: попытка
Qt создать EGL-поверхность для ОКНА приложения целиком (через
`wayland-egl` QPA платформу), НЕ то же самое, что передача текстуры
камеры через `android_wlegl`. Гипотеза: если заставить ОКНО
рендериться через SHM/software backing store (обычный небуферизованный
Wayland без EGL для самого окна) вместо `wayland-egl`, а текстуру
камеры вставлять поверх через уже рабочий `android_wlegl`-путь --
видео теоретически МОЖЕТ показаться, несмотря на то что окно как
таковое не хардварно-ускорено. Это уже требует патча кода (Qt Quick
scenegraph / `qt5-cameraplugin-aal`), не просто переменной окружения
-- полноценная задача на отдельную сессию с чтением исходников
wlroots `android_wlegl` протокола и Qt Quick software-рендеринга.
