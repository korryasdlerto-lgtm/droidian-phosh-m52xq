# v28: рассинхронизация версий между arm64/armhf в аудио-бандле (2026-09-01)

## Контекст

Живая прошивка v27 (полный вайп Data). Цель v27 была добавить 3
недостающих arm64 `.deb` (`libhardware2`, `libhybris-common1`,
`pulseaudio-modules-droid-modern`) в `halium-audio-fix-debs`, чтобы
закрыть WARNING в chroot-установке аудио-стека (см.
`FIXES-V27-ARM64-AUDIO-DEBS-AND-LIVE-DISCOVERIES.md`). Живой тест
изолированной установки этих 3 пакетов (через `dpkg -i` на уже
загруженной системе v26, с temporary `remount,rw /`) прошёл идеально
чисто -- но при реальном флеше v27 (все ~290 пакетов одной транзакцией)
WARNING остался, просто сместился на другой пакет.

## Диагностика

`/data/halium-audio-fix-chroot-install.log` (после флеша v27) показал:
```
dpkg: dependency problems prevent configuration of pulseaudio-modules-droid-modern:armhf:
 pulseaudio-modules-droid-modern:armhf depends on libhardware2 (>= 0.0.5.53).
dpkg: dependency problems prevent configuration of pulseaudio-modules-droid-hidl:
 pulseaudio-modules-droid-hidl depends on pulseaudio-modules-droid-jb2q | pulseaudio-modules-droid-modern
```
На этот раз падает **armhf**-вариант (раньше был arm64) --
`libhardware2:armhf` вообще ни разу не получает "Setting up" за весь
лог (только "Unpacking"). Более того, лог показывает странные
"Unpacking ... over (...)"-строки, где "предыдущая" версия для
`:armhf`-варианта совпадает с версией arm64-варианта -- явный
симптом путаницы dpkg при обработке пакета с РАЗНЫМИ версиями между
архитектурами в одной транзакции.

**Настоящая причина**: версии `libhardware2`/`libhybris-common1`
armhf и arm64 в бандле НЕ совпадали:
- `libhardware2`: armhf был `git20260707121655` (старый, из
  оригинального ~290-пакетного набора), arm64 -- `git20260812235837`
  (актуальный снапшот на момент добавления в v27).
- `libhybris-common1`: armhf `git20260707121655` (старый), arm64
  `git20260715172057` (взят из живого apt-кэша устройства, тоже
  старее актуального).

Проверка индекса `releases.droidian.org/snapshots/next/dists/rolling/
main/binary-{arm64,armhf}/Packages.gz` показала: АКТУАЛЬНАЯ версия
ОБЕИХ архитектур на сегодня -- `git20260812235837.91f805b` (то есть
даже armhf, который считался "родным" для бандла, давно устарел --
сам изначальный ~290-пакетный набор собирался в другую дату, чем
последний раз обновлялся апстрим-репозиторий). `pulseaudio-modules-
droid-modern` версии совпадали изначально (`14.2.103-1+droidian0+
git20240829212213.935726a`) -- этот пакет проблемы не создавал.

## Фикс (v28)

Скачаны и SHA256-сверены по индексу АКТУАЛЬНЫЕ версии для ОБЕИХ
архитектур сразу (не смешивать старое+новое между arm64/armhf):
- `libhardware2` arm64 + armhf, `git20260812235837.91f805b`
- `libhybris-common1` arm64 + armhf, `git20260812235837.91f805b`

Старые (рассинхронизированные) `.deb` удалены из
`halium-extras/rootfs-files/usr/local/lib/halium-audio-fix-debs/`,
заменены на новую согласованную пару для каждого пакета. Raw-`.so`
safety-net файлы (`usr/lib/aarch64-linux-gnu/libhybris-common.so.1*`,
`libhybris/linker/{n,q,o,mm}.so`) тоже пересобраны из НОВОГО
`libhybris-common1` arm64 `.deb`, для консистентности с тем, что
реально ставит dpkg.

**v27 НЕ трогался** (уже прошит с рассинхронизированными версиями,
подтверждённый WARNING) -- по правилам проекта, откачен обратно к
точному состоянию прошитого zip (старые версии восстановлены из v26 и
из кэша `/tmp` этой же сессии).

## Урок на будущее

При добавлении недостающей архитектуры для уже существующего в бандле
пакета -- ВСЕГДА проверять версию ОБЕИХ архитектур в актуальном
индексе репозитория и синхронизировать, а не просто добавлять
"какую-нибудь рабочую" arm64-сборку поверх старого armhf. Изолированный
живой тест (`dpkg -i` вручную, в обход полной ~290-пакетной
транзакции) НЕ гарантирует то же поведение в реальной транзакции --
дал ложно-позитивный результат именно из-за того, что тестировался на
УЖЕ настроенной системе, а не с нуля вместе со всеми остальными 290
пакетами разом.

## Дополнение: переделан автостарт контейнера -- единый механизм вместо пары "45с размаскирует 25с"

Живой тест v27 (реюз устройства с маркером `CONTAINER_ENABLED`,
оставшимся ещё от диагностики ДО v27) нашёл реальный edge-case в схеме
v27 ("45с одноразовый таймер на первую загрузку сам размаскирует
отдельный 25с-механизм для всех последующих"): если маркер уже
существует на момент первой загрузки НОВОЙ прошивки (пережил несколько
циклов флеш/тест в рамках одной диагностической сессии), 45с-юнит
корректно пропускает СЕБЯ (`ConditionPathExists=!...` не проходит) --
но раз он не запускается, он и не успевает выполнить свою же логику
размаскировки 25с-механизма. Итог: автостарт полностью сломан
НАВСЕГДА на этом конкретном устройстве, до следующего полного вайпа.

**Фикс (по прямому предложению пользователя)**: вместо пары юнитов
("одноразовый первый" + "маскированный/размаскируемый последующий") --
ОДИН постоянный `halium-container-autostart.service`/`.timer`
(`OnBootSec=25s`, работает КАЖДУЮ загрузку, ничем не маскируется).
Развилка "первый это раз или нет" -- целиком внутри самого скрипта
`halium-container-autostart.sh`:
```sh
if [ ! -f /userdata/CONTAINER_ENABLED ]; then
    sleep 20   # итого 45с с момента boot
    touch /userdata/CONTAINER_ENABLED
fi
systemctl start lxc-android-config.service
```
Никакой маскировки/размаскировки других юнитов не требуется в принципе
-- сама эта развилка не зависит от того, когда/сколько раз запускался
таймер раньше, только от текущего состояния маркера прямо сейчас.
Старый `halium-start-container-delayed.service`/`.timer` (из
`halium-restore-state.sh`) теперь избыточен и замаскирован НАВСЕГДА
(раньше -- временно, до первого успешного старта).

Старые файлы `halium-extras/{libexec,units}/halium-first-boot-
container-autostart.*` (схема v27) удалены из v28, заменены на
`halium-container-autostart.*`.

**НЕ протестировано живьём** -- нужен полный вайп Data, чтобы честно
проверить оба сценария (первая загрузка ~45с, вторая и далее ~25с) с
нуля, без унаследованного маркера.
